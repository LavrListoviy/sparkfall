# Архитектура и добавление контента

Актуально для **0.6.0**. Сначала прочитай [правила разработки](../AGENTS.md), [контракт штормовых сборок](ITERATION_3.md) и G01–G05 в [спецификации](SPEC.md). Здесь практическая карта проекта: куда идти с новым артефактом, событием или анимацией.

## Частоты глифов

`content.js` хранит `GLYPH_RULES` и словари `glyphBonus` у классов и артефактов. `glyphs.js` складывает бонусы уникальных источников и ограничивает каждый вес диапазоном 100–200, не расходуя RNG. У класса может быть свой бонус независимо от стартового артефакта.

Новый забег получает `glyphVersion: 1`; маршрут и шторм сохраняют свои отдельные версии. В начале боя `createBattle` рассчитывает профиль и передаёт его в `createBoard` четвёртым аргументом. Поле сохраняет `glyphWeights`, поэтому каскады, кратеры, перчатка и перестройки используют одну политику без передачи списка артефактов в геометрическую логику.

При свободном заполнении выбираем из пяти типов пропорционально весам. При создании стабильного поля или локальном восстановлении сначала исключаем готовые совпадения, затем выбираем по весам среди допустимых типов. Один выбор потребляет один вызов RNG. Существующие глифы не перекрашиваются.

Сохранения 0.3–0.5 получают `glyphVersion: 0`, сохраняют прежние пулы наград и точную последовательность RNG. У старого поля нет `glyphWeights`. Валидатор проверяет соответствие весов классу и артефактам самого боя: после награды завершённый бой ещё содержит предыдущий состав артефактов, а следующий получит новый. Отчёт включает `glyphVersion`, в том числе при экспорте перенесённой старой экспедиции.

Артефакт частоты добавляется данными `glyphBonus: {fire: 50}` и переводом описания, без нового обработчика боевого эффекта. Для текущих пяти предметов `introduced: 4` исключает их из прежних экспедиций. Изменение порядка контента или формулы генерации требует новой версии правил и проверки реплеев.

## Главное разделение

```text
Клик / свайп / клавиатура
        ↓
app.js → run.battleAction(session, action)
               ↓
          battle.js → board.js + Random
               ↓
       новое состояние + журнал + кадры эффектов
               ↓
app.js → saveSession() → buildTimeline() → BattleScene.play()
                                     ↘ HUD в момент попадания
```

**Результат хода вычисляется и сохраняется до начала анимации.** На экране он показывается постепенно. Закрытие вкладки посреди удара не отменяет урон, не возвращает потраченное действие и не перебрасывает награду.

`public/core/` не знает о Three.js, DOM, звуке или скорости анимаций. Рендерер не решает, сколько урона нанести, и не вызывает RNG. Это граница, которую стоит беречь: благодаря ей можно менять внешний вид и позже перенести правила на другой движок.

В обычном состоянии боя `session.run.battle` содержит поле, героя, массив из 1–3 врагов, индекс цели, шторм и RNG. Индексы клеток — от 0 до 48, слева направо, сверху вниз. `session.run` хранит здоровье и отрыв для перехода между комнатами. `profile` хранит общие искры, открытия и достижения.

Редьюсеры возвращают новое состояние. Недопустимое действие возвращает исходный объект: интерфейс по этому признаку понимает, что обмен бесплатный и анимацию результата запускать не нужно.

## Добавить артефакт

Пример ниже — **учебное расширение, не установленное в игру**: «Угольная шестерня», первая группа клинков за действие дополнительно наносит 6 базового огненного урона той же выжившей цели.

### 1. Сначала контракт

Добавь требование в спецификацию следующей итерации:

- Триггер: первая группа `steel` за успешный обмен, включая все каскады этого обмена.
- Порядок: обычный физический урон → дополнительный огонь.
- Огненный резист применяется к дополнительному урону; множители длины группы и Стеклянного реактора его не увеличивают.
- Эффект не вызывает другие артефакты повторно и не меняет цель. Если обычный удар уже убил цель, дополнительный урон пропадает; триггер всё равно потрачен.
- На следующем действии триггер снова доступен. Конец раунда сам по себе эффект не вызывает.
- Чертёж стоит 3 искры и добавляет артефакт в будущие награды.

Такие детали решают больше, чем красивое название. «Добавляет огонь» без порядка, цели и лимита — приглашение к багам.

### 2. Падающий тест

В `test/artifacts.test.js` или отдельном файле:

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { createBattle, applyGroups } from '../public/core/battle.js';

test('A17: cinder fires once across the groups of one action', () => {
  const initial = createBattle('cinder-test', { artifacts: ['cinder'], ruleset: 2 });
  const group = { type: 'steel', indices: [0, 1, 2] };
  const first = applyGroups(initial, [group]);
  const second = applyGroups(first, [group]);
  // Furnace: 110 HP, 50% fire resistance. Steel = 9, bonus fire = 3.
  assert.equal(first.enemies[0].hp, 98);
  assert.equal(second.enemies[0].hp, 89);
  assert.equal(initial.enemies[0].hp, 110);
});
```

Запусти `node --test test/artifacts.test.js` и убедись, что тест падает именно по ожидаемому урону. Затем добавь проверки смертельного основного удара, сброса лимита следующим `playSwap`, другого резиста и совместимости с существующими артефактами. `applyGroups` намеренно сохраняет `actionFlags` между вызовами; сбрасывает их начало нового действия в `playSwap`.

### 3. Запись в каталоге

В `ARTIFACTS` файла `content.js`:

```js
cinder: {
  name: 'Угольная шестерня', icon: 'fire', color: 'fire', cost: 3, introduced: 4,
  text: 'Первая группа клинков за действие дополнительно наносит 6 огненного урона той же выжившей цели.'
},
```

`cost: 0` делает обычный предмет доступным сразу. `rarity: 'rare'` исключает его из обычных наград: такой предмет выдаётся только за штормовую элиту. `introduced` помечает новое поколение предметов и исключает его из старых забегов. Положительная цена выводит чертёж в мастерской; открытие имеет ключ `artifact:cinder`. `run.reward()` автоматически собирает доступные, ещё не взятые артефакты из каталога. Отдельный список наград не нужен.

Иконка должна существовать в `icons.js`. Для нового символа добавь её туда; не вставляй SVG в боевые правила. Для стартового набора добавь запись в `LOADOUTS` с `artifact: 'cinder'`.

### 4. Реализация эффекта

В `applyGroups`, сразу после основного `damage(next, target, base, group.type)`:

```js
if (group.type === 'steel' && has(next, 'cinder') && !flags.cinder) {
  flags.cinder = true;
  damage(next, target, 6, 'fire', 'cinder');
}
```

`damage` проверяет живую цель, применяет резист, меняет HP и публикует событие через `emit`. Существующая анимация огненного удара и текст журнала подхватят событие автоматически. Не вызывай `applyGroups` рекурсивно ради дополнительного урона: это повторно запустит цепочку артефактов.

Не меняй HP напрямую без события: итог сохранится, но во время показа игрок увидит необъяснимый скачок здоровья. Новый тип эффекта потребует дополнить `eventText` в `app.js`, время в `timeline.js` и при необходимости визуал в `scene.js`.

### 5. Сохранение и проверка

`save.js` проверяет известные ID и выводит размеры коллекций из каталогов. Счётчики мастерской тоже вычисляются автоматически. Не удаляй и не переименовывай старые ID без миграции. Новый сохраняемый параметр требует проверки формата, значений по умолчанию для старых версий и теста возобновления.

Добавление предмета меняет пул наград и последовательность случайных выборов. Перед выпуском обнови версию правил и продумай совместимость старых отчётов: один только перевод текста версии не сохраняет детерминизм. Ниже описано, как мы сделали это для маршрута 0.3 → 0.4.

## Добавить случайное событие

Для выбора со здоровьем, лечением, искрами и временем отдельный обработчик не нужен. Например, «Застрявший лифт»:

```js
lift: {
  name: 'Застрявший лифт', icon: 'compass',
  text: 'Механизм дрожит над провалом. Можно восстановить питание или уйти по лестнице.',
  choices: [
    { id: 'repair', name: 'Починить привод',
      text: '−6 здоровья · +3 искры · шторм ближе на 1',
      hp: -6, embers: 3, time: 1 },
    { id: 'stairs', name: 'Пойти по лестнице',
      text: '+1 к отрыву от шторма', gap: 1 }
  ]
},
```

Порядок работы:

1. Опиши правила в спецификации, включая точные цены и ограничения.
2. Добавь тест через `startRun` → `enterNode` → `chooseEvent`; для направленного теста допустимо задать `session.run.route[0][0] = {...session.run.route[0][0], kind:'event', event:'lift', enemyIds: undefined}` перед входом. Это тестовая фикстура, не код интерфейса.
3. В тесте проверь HP 70 → 64, отрыв 4 → 3, +3 искры забега, следующий этаж и отсутствие повторного начисления при повторном вызове. Запусти его до реализации.
4. Добавь запись `lift` в `EVENTS`, затем ID в список `events` внутри `createRoute` в `routes.js`.
5. Получи зелёный тест, проверь сохранение и отображаемые последствия в браузере. Новая запись каталога сама по себе не появится на карте без включения в список генерации.

| Поле выбора | Значение |
|---|---|
| `hp` | Изменение HP; для цены используй отрицательное число |
| `heal` | Лечение по общей политике `healingBlock`; учитывает Сердце бури |
| `embers` | Искры текущего забега, начислятся в профиль при завершении |
| `time` | Сократить отрыв на указанное число |
| `gap` | Увеличить отрыв |

`choiceBlocked` — общий предикат для отключённой кнопки и редьюсера. Цена не может убить героя: при HP 6 выбор с `hp: -6` недоступен. Лечение проверяется по состоянию шторма **до** выбора, затем применяется цена времени. У нового забега отрыв ограничен только сверху числом 6; у старого — 0…6. Здоровье ограничено 70. В событиях метеориты не падают.

Если нужен обмен артефактами или новое последствие, сначала добавь его в контракт и `choiceBlocked`/`chooseEvent`, затем тесты. Не делай «магическую» ветку по названию события в `views.js`. Текст показывает уже определённое правило.

## Случайность и совместимость

- В правилах запрещены `Math.random()`, текущее время и случайность из анимации. `Random` создаётся из seed или сохранённого `rng`; после операции запиши новое `random.state`.
- Случайное предложение наград хранится в состоянии. Перерисовка или повторное открытие окна не генерирует его заново.
- `schema` описывает структуру сохранения, `version` — версию правил, `routeVersion` — вариант генерации маршрута.
- В 0.5.0 `parseSave` сохраняет версии маршрутов 0.3 (`1`) и 0.4 (`2`), назначая прежним боям `ruleset: 1`. Новые экспедиции используют маршрут `3` и бои `ruleset: 2`. Старый маршрут не переписывается посреди забега.
- `replayReport` учитывает версию маршрута. Контрольный старый отчёт `docs/browser-playthrough.json` по-прежнему должен заканчивать победой с 68 HP. Это полезный предохранитель от незаметного изменения правил.
- `waves` и `presentation` временные: `encodeSession` исключает их содержимое из файла. После перезагрузки показывается завершённый результат без повторного проигрывания старых атак.

## Графика и анимации

Сцена — ортографическая 2D-композиция в Three.js. Это осознанный выбор для пиксельных персонажей и матрицы. Камера не добавляет перспективные искажения. Спрайты, фон, поле, снаряды и числа рисует WebGL; текст, диалоги и прозрачные кнопки остаются в HTML для чёткости, фокуса, клавиатуры и доступных подписей.

`layout.js` возвращает координаты для обоих слоёв. Меняешь размер клетки — меняй общую геометрию, иначе визуальная клетка и область свайпа разъедутся.

`characters.png` — атлас 2×4; индексы и соответствия врагам находятся в `ATLAS` в `scene.js`. Фильтрация `NearestFilter`, без mipmaps, цветовое пространство sRGB. Происхождение и точная разметка изображений — в [ASSETS_PIXEL.md](ASSETS_PIXEL.md).

Текущая анимация персонажей — движение целого спрайта, выпад, реакция на попадание и снаряд. Отдельных нарисованных кадров ходьбы и атаки пока нет. Их можно добавить в атлас и выбирать UV-кадр в `animate(progress)`, не меняя боевую математику.

`emit` фиксирует промежуточный снимок сразу после эффекта: HP, статусы, цель и шторм; для изменения клеток — ещё и поле. `buildTimeline` заканчивает последовательность полным итоговым снимком. `BattleScene.play` обновляет HUD в момент попадания, затем оставляет короткую паузу. Длительность зависит от прошедших миллисекунд, а не количества кадров. В скрытой вкладке показ приостанавливается, шторм не идёт сам по себе.

Настройки 0,5× / 1× / 2× меняют только длительности. Уменьшение движения отключает выпады и тряску, сохраняя паузы и числа. Настройки живут в отдельном ключе `sparkfall.settings.v1`; профиль — в `sparkfall.save.v1`.

Three.js 0.187.0 закреплён в `package-lock.json`; файлы для браузера и MIT-лицензия лежат в `public/vendor/three/`. Обычному игроку не нужен npm install. Для обновления копии после установки зависимостей: `npm ci`, затем `npm run vendor`. CDN во время игры не используется. Нужен браузер с WebGL 2.

Официальные справочники: [ортографическая камера](https://threejs.org/docs/pages/OrthographicCamera.html), [материал спрайта](https://threejs.org/docs/pages/SpriteMaterial.html), [текстуры](https://threejs.org/docs/pages/Texture.html), [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html).

```powershell

```

Сначала падающий тест нового поведения, затем реализация и зелёный прогон. В браузере проверь новую механику при 0,5× и 2×, перезагрузку посреди эффекта, узкое окно, смерть цели и действие внутри шторма.

После проверки обнови версию, README, TODO и QA-отчёт. `npm run package` собирает переносимые каталоги `web/` и `playtest/`. Историю Git меняем только по отдельному запросу пользователя.


## Штормовые сборки и маршруты 0.5

Новый забег создаётся с `routeVersion: 3`, новый бой — с `ruleset: 2`. Для совместимости низкоуровневый `createBattle()` по умолчанию оставляет `ruleset: 1`; в новых тестах поведения передавай `ruleset: 2` явно. Продуктовый вход — `startRun()` → `enterNode()`, который выбирает правила автоматически.

### Единая политика

Не проверяй `gap === 0` в интерфейсе: расстояние теперь бывает отрицательным. Импортируй из `storm.js`:

- `inStorm(gap)` и `stormDepth(gap)` — положение героя, глубина 1 при нулевом отрыве.
- `nextMeteorDamage(battle)` — следующий удар с приближением фронта, реактором и текущим щитом.
- `meteorDamage(gap, ruleset)` — базовый урон 4 / 6 / 8. Усилитель и щит применяются затем в `hurt()`.
- `healingBlock(gap, artifacts, ruleset)` — `null`, `storm` или `heart`. Общий контракт для боя, событий, HUD и перечёркивания зелий.
- `actionLimit(artifacts, ruleset)` — два либо три действия.
- `travelGain(run, node)` и `travelForecast(run, node)` — переход с разгоном, условным компасом и верхним пределом отрыва 6.

`longGroupEffects()` в `battle.js` вызывается после основного эффекта каждой группы 4+: сначала заземление, затем ткань, затем линза. `actionFlags` ограничивает ткань и линзу одним срабатыванием за обмен, включая каскады. Прямые бонусы артефактов не вызывают этот обработчик повторно. Нестабильность разрешается раньше лечения; погибшего героя эффект не воскрешает.

### Редкость и условия награды

`battle.initialGap` фиксируется после перехода. В `battleAction()` редкая награда назначается только для элиты при `initialGap <= 0` и конечном `storm.gap <= 0`. `reward()` сохраняет три разных ещё не взятых ID и `rewardRarity` до открытия окна. Пустой редкий пул даёт 4 искры и `rewardExhausted: 'rare'`, обычный — 2. Не вычисляй условие в шаблоне окна: UI читает уже сохранённый результат.

### Добавить погодную встречу

Обычная запись в `EVENTS` использует прежние поля выбора; дополнительно `artifact: 'overclock'` выдаёт конкретный предмет, а `choiceBlocked()` запрещает повторную покупку. Цена в HP не должна убивать героя. Поле `time` углубляет шторм без метеорита в событии.

В узле маршрута укажи `{kind: 'event', event: 'fountain', stormEvent: 'ashCaravan'}`. `enterNode()` сначала применит переход, затем выберет вариант погоды и запишет `run.event`; перезагрузка его не перебросит. Новые варианты встраиваются в `createRoute()`; `next` содержит реальные ID разрешённых переходов. Карта и редьюсер используют один граф через `reachableNodes()`.

### Совместимость

Миграция 0.3/0.4 сохраняет прежний `routeVersion`, назначает `ruleset: 1`, нулевой щит и обычную редкость. Такие экспедиции по-прежнему имеют два действия, неотрицательный отрыв, переход +3 и прежний пул артефактов. Точные результаты старых отчётов закреплены тестами. Следующее изменение RNG или пула потребует новой версии маршрута/правил и собственного решения о миграции.


## Локализация и тексты

Выбор языка принадлежит представлению. `presentation/settings.js` хранит `language: 'ru' | 'en'` отдельно от профиля; старые настройки получают `ru`. Ядро, RNG, отчёты и сохранённые идентификаторы от языка не зависят.

- `i18n/messages.js` — целые строки интерфейса с семантическими ключами и именованными параметрами. `t(key, parameters)` выбирает язык, подставляет параметры и формы через `Intl.PluralRules`; числа форматирует `Intl.NumberFormat`. При отсутствии EN используется RU; отсутствие ключа или параметра вызывает явную ошибку.
- `core/content.js` — исходные числовые данные и RU-тексты; `i18n/content-english.js` — EN-тексты по тем же ID. `i18n/content-messages.js` собирает записи, `i18n/content.js` предоставляет представлению копии с динамическими текстовыми геттерами. Импортировать их в ядро нельзя.
- `i18n/document.js` переводит только явно помеченную оболочку (`data-i18n`, `data-i18n-aria-label`), `lang`, заголовок и описание страницы. Перевод не ищет русский текст в готовом DOM.
- `presentation/text.js` переводит структурированные события журнала и объявления для диктора заново при показе. Историю решений не нужно воспроизводить ради другого языка.
- `i18n/glossary-data.js` — единый источник 56 терминов. `glossaryView()` выводит их в игре; `npm run glossary` обновляет `docs/GLOSSARY.md`. Проверка точного соответствия входит в `npm test`.
- `typography.css` — локальный Cormorant Unicase для заголовков. Основной текст и цифры остаются в обычном шрифте; лицензия лежит рядом с TTF.

При добавлении артефакта, врага или события сначала зафиксируй механику и тесты, затем добавь RU и EN по одному ID. Переводи все намерения, варианты выбора и описания. Пользуйся [глоссарием](GLOSSARY.md) и [правилами вординга](LOCALIZATION.md#l03-вординг-и-глоссарий), после изменения терминов или названий запускай `npm run glossary` и `npm test`.

Не вставляй HTML в каталог. Разметка принадлежит шаблону, а пользовательские значения нужно экранировать на границе HTML. Seed, email, текст отзыва и диагностический JSON остаются исходными. Ошибки старого ядра переводятся адаптером `i18n/errors.js`; ошибки формы отзыва сохраняют ключ и параметры для повторного показа на другом языке.

## Экранная навигация

`presentation/navigation.js` хранит временный экран, вкладки, страницы и выделенные записи. Это состояние не входит в сохранение экспедиции. `navigate()` сохраняет независимый контекст разделов; `paginate()` ограничивает страницы; `routeSelection()` разрешает просмотр любого слоя, но проверяет возможность входа через прежний `reachableNodes()`.

`views.js` формирует главное меню, подготовку, мастерскую и экраны забега. `app.js` отделяет команды навигации от команд игрового ядра: покупка перерисовывает мастерскую с прежним выбором, переход в меню не завершает забег. Разрешение боевого действия блокирует уход из боя. После завершения действия его результат уже сохранён прежним способом.

`menus.css` задаёт оболочку по высоте окна и компактное окружение боя. Длинные коллекции используют список с выбранной записью и страницы. Не добавляй раскрывающиеся бесконечные списки в основное окно. Новые строки навигации лежат в `i18n/menu-messages.js`. Геометрию проверяй визуально согласно [контракту меню](MENUS.md), переходы — через `test/navigation.test.js`.
