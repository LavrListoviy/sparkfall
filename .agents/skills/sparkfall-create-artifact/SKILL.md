# Создание артефакта Sparkfall

Работай в корне репозитория, содержащем `public/core/artifact-catalog.js`. Пути в командах ниже относятся к этому корню. Ссылки рассчитаны на размещение навыка в `.agents/skills/sparkfall-create-artifact/`.

## Определить предмет

1. Прочитай [правила проекта](../../../AGENTS.md), [инструкцию редактора](../../../docs/ARTIFACT_EDITOR.md), текущий [каталог](../../../public/core/artifact-catalog.js) и [валидатор](../../../public/core/artifact-schema.js). Для порядка эффектов проверь [исполнитель правил](../../../public/core/artifact-rules.js). Схему и допустимые значения бери из текущего кода, не из памяти.
2. Найди похожие предметы: переиспользуй поддерживаемые возможности, но не меняй существующий предмет вместо запрошенного нового. Из запроса и контекста выдели событие, условия, цель, величину, лимит, порядок правил, редкость, цену и частоты. Уточняй только недостающие решения, влияющие на поведение или баланс. Название, перевод и подходящую существующую иконку можно предложить самостоятельно.
3. Для новой механики предмета запиши договорённость и критерии приёмки в [SPEC.md](../../../docs/SPEC.md), свяжи их с [TEST_PLAN.md](../../../docs/TEST_PLAN.md) и обнови [TODO.md](../../../TODO.md). Отделяй предложение баланса от уже согласованных чисел. Действующее согласование не запрашивай повторно. Если пользователь просил только концепт, остановись на концепте.
4. Если схема не выражает нужное поведение, обозначь конкретный пробел и используй [навык расширения эффектов](../sparkfall-extend-artifact-effects/SKILL.md) в согласованном объёме. Не выдавай приблизительную комбинацию за точное исполнение запроса.

## Собрать данные

- Добавляй определение в `ARTIFACT_CATALOG.items` файла `public/core/artifact-catalog.js`. `content.js` уже использует этот каталог; отдельная таблица новых предметов не нужна.
- Сохраняй ID, `introduced` и порядок существующих записей. Новый ID добавляй в конец; текущее поколение новых предметов и формат ID проверяй по валидатору. Не удаляй старые ID: для исключения из будущих наград есть `enabled`, с ограничениями для связанных с классами и событиями предметов.
- Заполняй RU/EN прямо в записи (`name`, `text`, `en.name`, `en.text`). Используй [правила локализации](../../../docs/LOCALIZATION.md) и [глоссарий](../../../docs/GLOSSARY.md). Описание должно точно отражать условия и лимит, особенно различие действия и раунда.
- Для обычной композиции оставляй `base: null`. Наследуй существующий базовый блок только намеренно: наследование плюс похожее собственное правило даст оба эффекта. Один базовый блок на нескольких предметах не умножается, правила каждого предмета независимы.
- `glyphBonus` задаёт прибавку к весу, а не процентные пункты вероятности. Редкость и цена определяют способ получения; сверяй их ограничения со схемой.
- Все поля правила обязательны по текущему контракту, включая неактивные в интерфейсе. У события без группы должны быть нейтральные `tile` и `min`.
- Не меняй [исторический каталог](../../../public/core/legacy-artifacts.js). Старые забеги и отчёты используют собственный снимок либо исторические определения. Правка текущего каталога применяется к новой экспедиции после обновления страницы.

Пример правила: первая подходящая группа клинков размером 4 или больше за действие накладывает 2 яда на исходную цель, если она пережила основной удар.

```json
{
  "trigger": "group", "tile": "steel", "min": 4,
  "weather": "any", "status": "any", "limit": "action",
  "effect": "poison", "amount": 2, "element": "poison",
  "target": "current", "ignoreStorm": false
}
```

Это фрагмент `rules`, не готовый предмет. Не добавляй пример в боевой каталог без запроса. Если основной удар убил цель, лимит всё равно потрачен. Условия статусов фиксируются до базового эффекта группы; наложение яда первым правилом не делает истинным условие «цель отравлена» второго правила того же события.

## Проверить и сохранить

1. Для нового игрового поведения сначала добавь содержательный тест в существующий набор и получи ожидаемое падение, затем добавляй данные. Проверяй наблюдаемый результат: HP, статусы, повторное срабатывание и границу условия. Тест нового каталожного предмета должен брать его из настоящего каталога, а не создавать внутри себя готовую копию реализации. В `createBattle` явно передавай `artifactCatalog`: значение по умолчанию предназначено для исторических правил. Примеры боевых проверок — [artifact-editor.test.js](../../../test/artifact-editor.test.js).
2. При программной правке прочитай текущий файл через `parseCatalog`, подготовь копию, проверь `catalogErrors(next, previous)` и сериализуй через `serializeCatalog`. Одна сериализация не проверяет неизменность относительно предыдущего каталога. Перед записью убедись, что исходник не изменён параллельно. Не исполняй импортированный пользователем JavaScript.
3. Если работа идёт через интерфейс, запусти `npm.cmd run editor`, используй «Стенд» и сохранение в проект. Конфликт ревизии требует перечитать актуальный каталог и перенести свои изменения. Не обходи защиту записью устаревшего файла поверх нового.
4. Для программной проверки используй `simulateArtifact(catalog.items, id, options)` из [artifact-sandbox.js](../../../public/core/artifact-sandbox.js) либо реальные редьюсеры боя. Стенд исполняет ядро, но не доказывает баланс полного забега.
5. Обнови генерируемый глоссарий и выполни проверки:

```powershell
npm.cmd run glossary
node --test test/artifact-catalog.test.js test/artifact-editor.test.js test/artifacts.test.js
npm.cmd test
npm.cmd run glossary -- --check
```

Промежуточный узкий прогон нужен для TDD, полный — после завершения изменений. Для одной правки текста не добавляй искусственные боевые тесты. Не редактируй генерируемый глоссарий вручную.

6. В браузере проверь карточку RU/EN и получение в новой экспедиции подходящим способом: чертёж/обычная награда либо редкая награда. На стенде проверь подходящее событие, неподходящее условие и повтор в пределах лимита. Если менялась вёрстка, проверь мышь, клавиатуру и узкий экран; отдельно укажи, проверялся ли физический телефон.
7. Отметь в TODO только проверенные пункты. В отчёте дай ID, итоговые правила, изменённые файлы, выполненные проверки и конкретные шаги QA. Сохраняй чужие изменения; публикация и изменение истории Git требуют отдельного поручения.
